═══ RETOUR EN ARRIÈRE n°1 (le plus important) : l'écrêtage IQR détruisait des
    colonnes entières ═══

  Symptôme observé : sur la heatmap de corrélation (section 6), la ligne/colonne
  `duis` était entièrement VIDE, et après préparation `duis` ne contenait plus
  que des 0. Une variable qui avait du sens au départ devenait une colonne
  constante et inutile.

  Cause (diagnostiquée sur les données) :
    La première version appliquait l'écrêtage IQR (Q1-1.5·IQR, Q3+1.5·IQR) À
    TOUTES les colonnes numériques sans distinction. Or duis a ~81 % de zéros :
        Q1 = 0 et Q3 = 0  →  IQR = 0  →  bornes = [0, 0]
        clip(0, 0) ramène TOUTES les valeurs non nulles (1882 personnes ayant eu
        un DUI) à 0. La colonne devient constante.
    C'est le défaut classique de l'IQR sur une variable de comptage "gonflée de
    zéros". Conséquence en cascade : variance nulle → corrélation de Pearson
    indéfinie (division par 0) → NaN → case vide dans la heatmap, et poids ≈ 0
    dans la régression logistique. Le même mécanisme rabotait aussi
    speeding_violations et past_accidents à un plafond trop bas (≤ 5), écrasant
    la queue (or un conducteur à beaucoup d'infractions est justement le plus
    intéressant pour un assureur).

  Solution choisie : écrêtage ADAPTATIF, une technique par TYPE de colonne
  (section5.py:40-79) :
    a) Catégorie / ordinal codé (entier, ≤ 10 modalités distinctes)
         → AUCUN écrêtage. Chaque valeur a un sens (0/1, tranche d'âge...).
         → concerne age, gender, vehicle_ownership, married, children,
           postal_code, ET duis (7 modalités).
    b) Comptage discret étalé (entier, > 10 modalités)
         → winsorisation DOUCE aux percentiles 1 % / 99 % : on ne rabote que les
           vraies queues extrêmes, sans toucher au cœur de la distribution.
         → annual_mileage (bornes 5000–18000), speeding_violations (0–10),
           past_accidents (0–7).
    c) Variable continue (non entière)
         → écrêtage IQR 1.5× classique. → credit_score (bornes 0.17–0.87).
    + GARDE-FOU universel : si b_inf >= b_sup, on saute (jamais d'écrêtage qui
      collerait les deux bornes → plus jamais de colonne effondrée). section5.py:72

  Conséquence (vérifiée) :
    - Plus aucune colonne constante.
    - duis préservé : 7 valeurs distinctes, corrélation réelle avec outcome
      = -0.189 (réapparaît dans la heatmap, le tableau de corrélations et les
      coefficients du modèle).
    - speeding_violations / past_accidents gardent leur queue (10 / 7 au lieu de 5).
  Aberrants finalement traités : credit_score 57 (IQR), annual_mileage 105,
  speeding_violations 91, past_accidents 80 (les 3 derniers en percentile 1/99).

  Pourquoi c'est la bonne décision : l'objectif de l'étape "aberrants" est de
  LIMITER les points trop excentrés, pas de RÉÉCRIRE la distribution. L'IQR
  aveugle faisait le second. La méthode par type respecte le sens des données.

═══ COMPRENDRE LA NORMALISATION (expliqué simplement, sans prérequis) ═══

  Après préparation, on remarque deux choses qui surprennent : les colonnes sont
  "centrées autour de 0", et certaines valeurs (comme duis) deviennent NÉGATIVES.
  Voici pourquoi, en partant de zéro.

  C'est quoi normaliser (StandardScaler) ?
    Les variables n'ont pas les mêmes unités : annual_mileage se compte en milliers
    de km, gender vaut 0 ou 1, age est une petite tranche. Si on laisse comme ça,
    l'algorithme croit que annual_mileage (avec ses gros chiffres) est "plus
    important" juste parce que ses nombres sont gros. Injuste.
    Pour rétablir l'égalité, on met toutes les colonnes sur la MÊME règle graduée
    avec cette formule, appliquée à chaque valeur d'une colonne :

         valeur normalisée = (valeur − moyenne de la colonne) / écart-type

    - "moyenne" = la valeur typique de la colonne.
    - "écart-type" = de combien les valeurs s'éloignent en général de la moyenne.

  Pourquoi tout est centré à 0 ?
    Parce qu'on SOUSTRAIT la moyenne à chaque valeur. Du coup la nouvelle moyenne
    de la colonne devient forcément 0, et l'écart-type devient 1. Toutes les
    colonnes finissent avec la même "taille". Une valeur normalisée se lit alors :
        = 0   → la personne est dans la moyenne pour cette variable
        > 0   → au-dessus de la moyenne
        < 0   → en-dessous de la moyenne
    Donc un nombre négatif ne veut PAS dire un nombre négatif de quoi que ce soit.
    Il veut juste dire "en-dessous de la moyenne".

  L'exemple de duis (pourquoi il part dans les négatifs) :
    Au départ, 81 % des gens ont 0 DUI, et une minorité en a 1, 2, 3...
    Cette minorité tire la moyenne vers le haut : moyenne de duis ≈ 0,24
    (alors que la valeur la plus fréquente est 0). L'écart-type ≈ 0,55.
    On applique la formule :
        duis = 0  →  (0 − 0,24) / 0,55 = −0,43   ← les 81 % à 0 passent en négatif
        duis = 1  →  (1 − 0,24) / 0,55 = +1,37
        duis = 2  →  (2 − 0,24) / 0,55 = +3,17
        duis = 3  →  (3 − 0,24) / 0,55 = +4,98
    Conclusion : les gens à 0 DUI sont SOUS la moyenne (0,24), donc leur valeur
    normalisée est négative (−0,43). C'est mécanique et parfaitement normal.

  Et la forme "décalée" du graphe ?
    La normalisation change l'ÉCHELLE, pas la FORME. duis reste très asymétrique
    (un gros pic à 0, une longue traîne vers le haut). Après centrage, le centre 0
    se cale sur la MOYENNE, pas sur le pic. C'est pourquoi le gros pic se retrouve
    un peu à gauche de 0 (à −0,43) avec une traîne qui s'étire vers la droite.
    Rien d'anormal : c'est le portrait fidèle d'une variable de comptage.

═══ CHOIX D'ENCODAGE : ordinal explicite plutôt que LabelEncoder ═══

  Problème de LabelEncoder : il code les catégories par ordre ALPHABÉTIQUE.
  Pour des variables ORDINALES (qui ont un ordre naturel), ça donne n'importe
  quoi. Exemples concrets observés :
    education : alphabétique → high school=0, none=1, university=2
                (absurde : 'none' devrait être le plus bas, donc 0)
    income    : alphabétique → middle=0, poverty=1, upper=2, working=3
                (aucun rapport avec le niveau de revenu réel)
  Comme on normalise ensuite et qu'on entraîne un modèle linéaire, un mauvais
  ordre brouille la relation entre la variable et outcome.

  Solution : on fixe nous-mêmes l'ordre logique de chaque colonne dans le dict
  ORDRE_ENCODAGE (défini dans data.py, partagé avec la section 4). L'indice = le code.
    driving_experience : 0-9y=0, 10-19y=1, 20-29y=2, 30y+=3
    education          : none=0, high school=1, university=2
    income             : poverty=0, working class=1, middle class=2, upper class=3
    vehicle_year       : before 2015=0, after 2015=1   (chronologique)
    vehicle_type       : sedan=0, sports car=1         (binaire, sens choisi)
  Garde-fou : une colonne non prévue retombe sur un tri alphabétique par défaut.

  Conséquence : pour driving_experience l'ordre était déjà bon par chance
  (l'alphabet coïncidait), mais education, income et vehicle_year sont corrigés.
  Effet mesuré faible sur l'accuracy (0.848 → 0.847) car ces variables sont
  secondaires, mais le modèle et les corrélations ont maintenant un SENS lisible.

  Bonus : cette refonte a supprimé la dette _encodeurs_export() (qui refaisait un
  fit de LabelEncoder juste pour afficher le mapping). show_encodage() lit
  désormais directement ORDRE_ENCODAGE. LabelEncoder n'est plus importé du tout.

Appris / à dire dans le rapport (questions implicites du PDF §5) :
  - NA imputés par médiane/mode car < 1/3 des données (sinon on aurait supprimé).
  - Encodage ORDINAL : on a choisi l'ordre logique de chaque catégorie au lieu de
    laisser LabelEncoder trier par ordre alphabétique (qui n'a pas de sens ici).
  - Normalisation StandardScaler car les algos marchent mal quand les échelles
    diffèrent (ex. annual_mileage en milliers vs gender en 0/1).
  - LEÇON forte : ne jamais appliquer une recette de nettoyage aveuglément ;
    adapter au type réel de chaque variable.

Réponses aux 3 questions du PDF §8 (à recopier dans le rapport) :
  1. Hypothèse : log( p(y=1|x) / p(y=0|x) ) = w·x + b
     → le log-rapport des probabilités (le "logit") est LINÉAIRE en x.
  2. Minimisation : on minimise la log-vraisemblance négative. Pas de solution
     analytique → méthode ITÉRATIVE (descente de gradient, Newton, L-BFGS qui est
     le solveur par défaut de scikit-learn).
  3. Paramètres appris : les poids w (un par variable d'entrée) et le biais b.

  - La classe positive est 1 (= sinistre).

Résultats (jeu de test, à mettre dans le rapport) :
  - Accuracy  = 0.835  (part de bonnes prédictions toutes classes confondues)
  - Précision = 0.739  (parmi les "sinistre" prédits, combien en sont vraiment)
  - Rappel    = 0.732  (parmi les vrais sinistres, combien on en retrouve)
  - F1-score  = 0.736  (moyenne harmonique précision/rappel)
  - Matrice : TN=1211, FP=162, FN=168, TP=459.

Définitions (à recopier) :
  - Accuracy = (TP+TN) / total. Trompeuse si classes déséquilibrées : ici prédire
    toujours 0 donnerait déjà ~69 %. C'est pourquoi on regarde aussi précision/rappel.
  - Précision = TP / (TP+FP). "Quand je dis sinistre, ai-je raison ?"
  - Rappel = TP / (TP+FN). "Est-ce que je rate des sinistres ?"
  - F1 = compromis entre les deux. Ici précision ≈ rappel ≈ 0.73 : le modèle est
    équilibré sur la classe minoritaire, c'est correct vu le déséquilibre 69/31.
